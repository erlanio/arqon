Diagramas e modelagens em JSON

Cada arquivo guarda elementos editáveis, propriedades e relações. Use este guia para criar integrações, gerar diagramas por código ou modificar um exemplo sem perder o significado do modelo.

Caminho mais seguro: abra um diagrama no editor, use Ver exemplo ou crie elementos, exporte pelo menu Arquivo, altere uma cópia do JSON e importe novamente. Os arquivos exemplo-*.json na raiz são modelos completos e importáveis.

Estrutura e importação

Existem quatro famílias de arquivo. O editor principal reúne conceitual, lógico, fluxograma, casos de uso e iStar; os três editores UML têm modelos próprios. Não misture objetos de uma família com outra.

Projeto do editor principal

Um projeto contém vários diagramas. active aponta para o diagrama aberto; openDiagramIds lista as abas abertas. O exemplo abaixo é um arquivo completo mínimo para um fluxograma:

{
  "id": "projeto-exemplo",
  "title": "Meu projeto",
  "active": "fluxo-1",
  "openDiagramIds": ["fluxo-1"],
  "diagrams": [{
    "id": "fluxo-1",
    "type": "fluxo",
    "title": "Fluxo inicial",
    "nodes": [{"id": "inicio", "kind": "start", "title": "Início", "x": 120, "y": 120, "fields": []}],
    "edges": []
  }]
}

O documento exportado pelo espaço principal envolve o projeto em {"format":"brmodelo-studio-document","version":1,"project":{...},"diagramId":"..."}. Para criar um arquivo manualmente, um projeto simples como o exemplo acima também pode ser importado. Mantenha diagramId, active e IDs das abas coerentes com o diagrama escolhido.

Regras comuns

  • Use JSON válido em UTF-8: aspas duplas, sem comentários e sem vírgula final.
  • Crie IDs únicos por elemento e mantenha as referências entre IDs. Nomes visíveis podem se repetir; IDs não devem.
  • No editor principal, todo nó usa id, kind, title, coordenadas numéricas finitas x/y e fields (mesmo quando vazio). Toda aresta usa id, from e to com IDs de nós existentes.
  • type do diagrama seleciona o editor. Já kind identifica o tipo de nó; type ou kind de uma relação define sua semântica conforme o editor.
  • Coordenadas e rotas controlam a aparência. Propriedades como cardinalidade, chaves, guardas e dependências controlam o modelo. Revise ambos após importar.
Editor principal · type: "conceitual"

Modelo conceitual de dados

As entidades, os relacionamentos e os atributos são nós separados. Uma relação conceitual é um losango com kind: "relationship", ligado por arestas às entidades participantes. Atributos também são nós ligados ao seu proprietário; não monte atributos como colunas da entidade.

diagram.conceptual guarda a notação e metadados, como {"version":1,"notation":"chen","specializations":[],"constraints":[]}. Entidades usam conceptual.entityKind; atributos e relações têm propriedades próprias. As pontas das arestas podem guardar fromMin, fromMax, toMin e toMax. Relacionamentos n-ários precisam de uma aresta por participante.

{
  "id": "ent-cliente", "kind": "entity", "title": "Cliente",
  "x": 180, "y": 290, "fields": [],
  "conceptual": {"entityKind": "strong", "partialKey": ""}
}

Ao converter para lógico, o editor cria outro diagrama; o conceitual original permanece. Revise as chaves e tipos SQL do resultado. Baixar exemplo conceitual completo.

Editor principal · type: "logico"

Modelo lógico de dados

Cada nó kind: "table" representa uma tabela. fields é o array de colunas; cada coluna tem id, name, type, size, key e nullable. primaryKey contém IDs de colunas da própria tabela. schema pode ser vazio.

{
  "id": "cliente", "kind": "table", "title": "cliente",
  "x": 180, "y": 290, "schema": "",
  "fields": [
    {"id": "cliente-id", "name": "id_cliente", "type": "INTEGER", "size": 11, "key": "PK", "nullable": false}
  ],
  "primaryKey": ["cliente-id"]
}

Arestas ligam a tabela dependente (from) à referenciada (to). O objeto foreignKey descreve a coluna de referência; os campos fromMin/fromMax/toMin/toMax registram cardinalidades. Ao gerar SQL para MySQL, MariaDB, PostgreSQL ou SQLite, confira nome, tipo, nulidade e coerência entre colunas, PK e FK. Baixar exemplo lógico completo.

Editor principal · type: "fluxo"

Fluxograma

Etapas são nós, por exemplo start, inputOutput, process, decision e end. A sequência de execução é definida por arestas. Uma decisão costuma ter saídas com label diferente, como “Sim” e “Não”.

{
  "id": "fluxo-aprovado", "from": "decisao", "to": "concluir",
  "label": "Sim", "direction": "forward", "lineType": "straight",
  "comment": "", "route": {"corners": [], "curves": {}}
}

route altera a linha desenhada, não os nós de origem e destino. Use a validação e a simulação do editor para conferir decisões e caminhos alcançáveis. Baixar exemplo de fluxograma.

Editor principal · type: "usecase"

Casos de uso UML

Use actor para atores, useCase para casos e systemBoundary para o limite do sistema. O limite usa width e height além de x/y. As arestas usam type igual a association, include, extend ou generalization.

{
  "id": "rel-consulta", "from": "ator-cliente", "to": "uc-consultar",
  "type": "association", "label": ""
}

Associação liga ator a caso; include e extend ligam dois casos; generalização liga dois atores ou dois casos. Em extend, extensionPoint pode referenciar um ponto do caso estendido. A direção from → to importa nessas relações. Baixar exemplo de casos de uso.

Editor principal · type: "istar"

Modelagem iStar 2.0

diagram.istar define version: "2.0", view (SD ou SR) e estereótipos. Atores usam istarBoundary, istarAgent ou istarRole; elementos intencionais usam istarGoal, istarQuality, istarTask ou istarResource.

{
  "id": "dep-cliente-plataforma", "from": "actor-cliente",
  "to": "agent-plataforma", "type": "dependencyGoal",
  "dependumKind": "goal", "dependum": "Pedido processado",
  "documentation": "Dependência do cliente",
  "route": {"corners": [], "curves": {}}
}

Em cada elemento intencional, node.istar.ownerId aponta para o ator proprietário. Dependências dependencyGoal, dependencyQuality, dependencyTask e dependencyResource ligam atores e descrevem o dependum. Refinamentos e contribuições ligam elementos intencionais do mesmo ator. Outros tipos incluem qualification, neededBy, isA e participatesIn. Baixar exemplo iStar completo.

Editor UML · format: "brmodelo.uml-activity"

Atividades UML

O arquivo é um projeto com version: 1, diagrams, activeDiagramId e profiles. Cada diagrama separa semântica em model e posição em view. model.nodes contém id, kind, name, properties, partitionIds e parentId; model.edges usa sourceId/targetId, kind (control ou object) e pode ter guard, weight e documentação.

{
  "id": "validar-dados", "kind": "action", "name": "Validar dados",
  "documentation": "", "properties": {"body": "Conferir pedido"},
  "stereotypes": [], "partitionIds": [], "parentId": null
}

Partições ficam em model.partitions. As coordenadas dos nós e a geometria das arestas ficam em view.nodes e view.edges, indexadas pelo ID semântico. Ao adicionar ou remover um elemento, mantenha modelo, referências e visão sincronizados. Baixar projeto de atividades completo.

Editor UML · project.format: "brmodelo.uml-class"

Classes UML

A exportação de documento usa format: "brmodelo-uml-class-document", version: 1, project e diagramId. No projeto, classifiers guarda classes, interfaces e enumerações; relationships guarda associações e outras relações. diagrams são visões desses mesmos elementos.

{
  "id": "cliente", "kind": "class", "name": "Cliente",
  "visibility": "public", "isAbstract": false, "isLeaf": false,
  "attributes": [], "operations": [], "literals": [],
  "templateParameters": [], "stereotypes": [], "constraints": [],
  "documentation": "", "representation": "classifier",
  "compartments": {"attributes": true, "operations": true}, "parentId": null
}

Atributos e operações pertencem ao classificador. Cada relação usa sourceId e targetId de classificadores, com pontas sourceEnd/targetEnd para multiplicidade, papel e navegabilidade. Cada diagrama seleciona IDs em elementIds/relationshipIds; view.nodes e view.edges posicionam esses IDs. Criar outro diagrama não duplica a classe semântica. Baixar exemplo de classes completo.

Editor UML · project.format: "brmodelo.uml-sequence"

Sequência UML

A exportação de documento usa format: "brmodelo-uml-sequence-document", version: 1, project e diagramId. Cada diagrama tem lifelines, messages, occurrences, executions, fragments, constraints, gates e view.

{
  "id": "msg-login", "kind": "sync", "name": "autenticar()",
  "sourceId": "usuario", "targetId": "sistema", "y": 150,
  "sendOccurrenceId": "envio-login",
  "receiveOccurrenceId": "recebimento-login", "executionId": "ativacao-login"
}

sourceId/targetId apontam para linhas de vida. Os IDs de ocorrência e ativação apontam para objetos nos arrays correspondentes; cada ocorrência também referencia a mensagem e sua linha de vida. A ordem vertical é dada por y. view.lifelines[id] guarda x, top e bottom. Como uma mensagem envolve várias referências, crie uma no editor e use o JSON exportado como molde para alterações por código. Baixar exemplo de sequência completo.

Antes de compartilhar ou integrar

  1. Parta de um exemplo completo do mesmo editor ou de um arquivo exportado pela versão atual.
  2. Valide a sintaxe com python3 -m json.tool arquivo.json ou outro parser JSON.
  3. Confirme IDs, referências, arrays e metadados do formato; JSON sintaticamente válido ainda pode ser um modelo inválido.
  4. Importe uma cópia no ARQON, use Validar, confira o desenho e exporte novamente para verificar a interpretação.

Esta página descreve os formatos usados pelo projeto hoje; não é uma especificação JSON Schema formal. Os exemplos completos e os módulos *-model.mjs do repositório são a referência para campos e regras adicionais.
